## 1. Как я понимаю задачу (мои слова)

Команды (2–3 разработчика на проект) сейчас пишут код «голым» Claude Code по ТЗ клиента.
ТЗ расплывчатое → Claude Code додумывает → баги → перегруженный manual QA.
Бэк и фронт блокируют друг друга при передаче API (долго ждать + долго объяснять).

Кит `sdd-kit` = OpenSpec 1.13.0 + Claude Code + hooks + CI, который:

1. **До кода** проводит deep dive: ИИ задаёт структурированные вопросы, на них отвечают
   разработчики **и PO/PM**, ответы проверяются на расплывчатость и противоречия,
   итог подтверждается человеком. Только потом — proposal/specs/design.
2. Делает из ответов **спеку, по которой бэк и фронт работают параллельно**, не дёргая друг друга.
3. Ведёт разработку по **TDD**, где тесты выводятся из сценариев спеки (а не «тесты ради тестов»),
   с гейтом полного прогона и E2E на ключевых сценариях.
4. Ставится в проект и на машину разработчика **быстро и без усилий**.

## 3. Предварительные идеи до ответов (устарело — см. раздел 6; contract-first отменён в Q19)

- **Контракт-first артефакт** в схеме `clarify`: между `specs` и `design` (или внутри design)
  появляется `api-contract` (OpenAPI-фрагмент / изменения эндпоинтов) со сценариями ошибок.
  Фронт генерирует типы и моки (например MSW) из контракта и начинает сразу. CI бэка проверяет,
  что реализация совпадает с контрактом (drf-spectacular diff). → закрывает G2.
- **Адресаты вопросов**: каждый вопрос помечен `Ask: PO | Dev | QA`; PO/PM отвечают в
  md-файле через GitHub (PR с questions-файлом) без Claude Code. Hook/CI проверяют заполненность. → G3.
- **Качество тестов** (G5): тест обязан нести маркер сценария; одна проверка поведения на
  сценарий через публичный интерфейс; запрет мокать тестируемый модуль; опционально
  mutation testing на изменённых файлах как метрика; ревью-агент тестов по чек-листу.
- **Manual QA**: verification-plan генерирует чек-лист для ручного QA только по сценариям
  уровня `manual` → QA проверяет меньше и целенаправленнее.

## 5. Сводка ответов (что решено)

- **Кто отвечает:** только разработчик, который ведёт фичу. Бизнес-вопросы он сам пересылает PO/PM.
  Поэтому кит помечает такие вопросы (`For: PO/PM`) и пишет их так, чтобы их можно было переслать как есть [Q1, Q18].
- **Откуда ТЗ:** документ, задача в трекере, устно или в мессенджере (Figma нет). Кит должен принимать
  исходный текст или файл ТЗ как источник для вопросов [Q2].
- **Что болит на стыке бэк/фронт:** контракта нет заранее, документация отстаёт, API меняется по ходу [Q3].
- **Порядок работы:** **сначала бэк, потом фронт** (contract-first отменён). Цель №2 значит: когда бэк готов,
  фронт стартует без вопросов и переписки. Ожидание самой реализации — это нормально [Q4→Q19, Q21].
- **Что бэк передаёт фронту:** **авто-handoff документ** (эндпоинты, поля, ошибки, права, примеры),
  собранный из спеки и OpenAPI-диффа [Q22].
- **Split-репозитории:** их в компании много, и это надолго. Новые проекты владелец будет предлагать делать в монорепо (D7 остаётся).
  Источник истины — бэк-репо, фронт только читает: командой кита или через OpenSpec `references` [Q6, Q20].
- **Фронтенд:** стек бывает разный, поэтому кит стек-независимый. Команды прописываются в `verify.yaml`, отдельного пресета под фреймворк нет [Q5].
- **Глубина вопросов:** полнота важнее скорости. **D4 меняется: по умолчанию Comprehensive**.
  Для мелких правок есть `lean` без вопросов [Q10, Q17].
- **Плохие тесты:** это тесты со слабыми assert'ами и тесты, не связанные с требованиями [Q7].
  Контроль: правила + трассируемость сценарий→тест + **ревью-агент тестов** перед завершением apply [Q8].
- **TDD:** tdd-guard остаётся главным стражем TDD, кит его не дублирует [Q9].
- **Manual QA:** кит его пока не касается. На будущее: QA утверждает тесты [Q11].
- **Распространение:** приватный GitHub-репо, установка `npx github:<org>/sdd-kit install` [Q12].
- **ОС:** Linux / macOS / WSL [Q13]. **Сроков нет**, качество важнее [Q14].
- **Метрики успеха:** баги от QA на фичу, lead time, ожидание фронта, отзыв команды.
  Считаются **вне кита**, потому что дашборды — non-goal [Q15, Q16].
- **Non-goals:** другие AI-инструменты, интеграция с трекерами, дашборды/метрики, нативный Windows [Q16].

## 6. Что меняется в архитектуре и фазах (предложение)

1. **Схема `clarify`**
   - по умолчанию глубина Comprehensive;
   - в начале `clarifications.md` раздел `## Sources`: `[desc]` — описание от разработчика,
     `[doc]` — файл или текст ТЗ, положенный в change;
   - у каждого вопроса строка `For: Dev | PO/PM`. Вопросы для PO/PM написаны без технических терминов,
     чтобы их можно было переслать как есть.
2. **Handoff бэк → фронт (новое, цель №2)**
   - в бэк-change новый артефакт **`frontend-handoff.md`**: пишется в конце apply, до archive;
   - источники: дельта-спеки и OpenAPI-дифф (команда экспорта схемы в `verify.yaml`, напр. `contract.export`);
   - содержимое: эндпоинты, поля и типы, ошибки и коды, права, пагинация, примеры запросов и ответов,
     что изменилось относительно прошлой версии API;
   - check `check-handoff`: каждый изменённый эндпоинт из OpenAPI-диффа описан в handoff;
     archive-gate требует этот документ, если API менялся;
   - фронт-сторона: команда кита (напр. `/handoff-import` или `install`-адаптер `split-frontend`)
     читает handoff из бэк-репо через `references`. Фронт-change начинается с handoff как `[doc]`-источника,
     вопросы — только про UI/UX.
3. **Тесты (цель №5)**
   - в `testing.md` правило: каждый `THEN` сценария проверяется конкретным assert'ом на
     наблюдаемый результат; никаких «assert status == 200» без проверки payload;
   - новый агент **`test-reviewer`**: получает спеку, verification-plan и diff тестов, проверяет силу
     assert'ов и связь с требованиями, выдаёт findings. Запускается перед завершением apply;
   - mutation testing → Ideas for later.
4. **TDD:** кит не принуждает Red→Green; пресет `django` рекомендует tdd-guard. Гейты кита: трассируемость, full-suite, E2E.
5. **Playwright-пресет** стек-независимый: `baseURL` и `webServer` берутся из `verify.yaml`.
6. **Установщик:** в репо кита нужен `package.json` с `bin` (без зависимостей), чтобы работал
   `npx github:<org>/sdd-kit`. С D3 не конфликтует. Проверить в фазе 4.
7. **Фазы:**
   - фаза 1: + Sources, `For:`, Comprehensive;
   - **новая фаза 6 «Handoff»** после фазы 5 (verification): `frontend-handoff`, `check-handoff`,
     команда импорта на фронте. CI → фаза 7, остальные фазы сдвигаются на одну;
   - фаза «Reviewer»: + `test-reviewer`;
   - фаза «Store adapter» переименовывается в **«Split adapter»**: сначала `references` (бэк — источник,
     фронт читает), эксперименты со Stores вторичны.
   - Пилот — **после фазы 5, как было** (решение владельца); handoff проверяется в пилоте позже.

## 7. Предлагаемые правки в `docs/goals.md` (сам файл не трогаю)
