# Идея: скриншоты UI как источник требований (после пилота 0.4)

Статус: отложено до окончания пилота стадии тест-кейсов (0.4.0-beta.1). Делать отдельным изменением
`/opsx:new add-ui-sources` на схеме `clarify-ai-qa`.

## Проблема

В ТЗ часто не написано то, что есть в UI: кнопка, которая что-то запускает, фильтр, массовое действие.
Если макет попадает к ИИ только на apply, такие элементы либо теряются, либо всплывают после того, как scope
уже согласован.

## Почему скриншоты, а не Figma MCP

Официальная Figma MCP и REST API на бесплатном плане ограничены примерно 6 чтениями в месяц (с 17.11.2025;
считается план файла). Сторонние MCP через REST упираются в тот же лимит. Мосты через плагин (Plugin API) лимитов
не имеют, но это сторонний код с широким доступом. Скриншоты бесплатны и не зависят от инструмента дизайна.

- https://developers.figma.com/docs/rest-api/rate-limits
- https://help.figma.com/hc/en-us/articles/34963238552855

## Решение (черновик)

**Когда:** вместе с ТЗ, до Main-раунда: `/opsx:new` → положить файлы в `sources/` → `/opsx:continue`.

**Куда и в каком виде:**

```
openspec/changes/<name>/
  sources/
    D1.md
    ui/
      01-orders-list.png
      02-orders-list-empty.png
      04-export-modal.png
      05-export-modal-mobile.png
      screens.md        # необязательные заметки: переходы, что игнорировать, ссылка на фрейм
  ui-inventory.md       # пишет ИИ
```

- PNG, один фрейм — один файл, экспорт 1x, длинная сторона ~1500–2000 px (длинные страницы резать).
- Имя `NN-экран-состояние[-mobile].png`; каждое состояние (пусто, ошибка, загрузка, модалка, dropdown, шаг
  формы) — отдельный файл.
- Прототип ИИ не читает: переходы описываются словами в `screens.md`.

**Что делает ИИ:**

1. Регистрирует каждый скрин как источник `[U<n>]` в `## Sources` (рядом с `[desc]` и `[D<n>]`).
2. До вопросов пишет `ui-inventory.md`: по экрану таблица Element / Type / What it seems to do / Source /
   Decision / Covered by.
3. Вопросы Main-раунда в обе стороны: «в UI есть, в ТЗ нет», «в ТЗ есть, в UI нет», не нарисованные
   состояния.

**Гейты (детерминированные, как coverage у тест-кейсов):**

- Main-раунд не закрывается (нет `proposal.md`), пока у каждого элемента нет Decision: in scope / out of
  scope `[Q<n>]` / decoration.
- Specs-раунд не закрывается (нет `design.md`), пока у каждого in-scope элемента нет существующего сценария в
  Covered by.
- Картинка в `sources/ui/`, которой нет в описи, блокирует следующий артефакт: ИИ дописывает опись и задаёт
  вопросы только по новым элементам.

**Дальше по цепочке:** тест-кейсы из сценариев (UI-элементы получают `e2e`), сопоставление компонентов в
design, скриншоты перед глазами на apply, эталон для визуального сравнения в будущем этапе E2E (Playwright).

## Решения, которые нужно подтвердить в clarify

- UI-режим включается по наличию `sources/ui/`, а не отдельной схемой: скриншоты — входные данные, как
  `[D<n>]`; иначе схем станет шесть. Работает во всех трёх clarify-схемах, не в `lean`.
- Дизайн-токены (цвета, шрифты, отступы) один раз на проект в репозитории — нужно ли это киту или это
  остаётся проекту.
- Что взять из пилота: если в пилотном проекте есть фронт, попробовать вручную (скрины в `sources/ui/` и
  просьба составить опись) до кода в ките.
