# Spec review — add-qa-test-cases-stage

Verdict: NOT-READY

| ID | Severity | Where | Finding | Evidence | Suggested action |
|---|---|---|---|---|---|
| S1 | major | test-cases/review › "What the AI QA reviewer checks", "Missing behaviour goes into the spec" | The AI QA reviewer reports "a requirement without an error case", but every test case must sit under an existing scenario. When the missing error case has no scenario in the spec, the fix needs a spec change. The specs only say what happens when a *human QA remark* shows missing behaviour, so a developer cannot tell whether the AI may add a scenario to fix a reviewer finding, or must ask, or should only add a case. | review/spec.md:19, :24, :105; document/spec.md:19; clarifications.md Q4, Q20 (both talk about "QA") | Follow-up question: "If the AI QA agent's finding shows behaviour missing from the spec (for example, the spec has no error scenario), what does the AI do? A. Adds the scenario to the spec and test cases for it, like with a human QA remark (and the spec reviewer runs again). B. Asks the developer first. C. Something else." |
| S2 | major | test-cases/review › "Missing behaviour goes into the spec" | Q20 (B) says the AI changes the spec and the test cases when a QA remark contradicts a confirmed answer. That usually means *changing or removing* an existing scenario, not adding one. The requirement and its scenarios cover only adding a scenario. Re-running the spec reviewer is also limited to "a scenario was added", but Q29 says "по изменённым спекам". There is nothing on what happens to the test cases of a scenario that is renamed or removed, or to tests that already reference them. | review/spec.md:105-116; clarifications.md Q20, Q29 | Widen the requirement to cover adding, changing and removing scenarios. Add scenarios for "Remark changes an existing scenario" (the scenario text is changed, its cases are revised, the spec reviewer runs again) and "Remark removes a scenario" (its test cases are removed). |
| S3 | major | test-cases/review › "Remarks are answered by the AI and closed only by QA", "Stage completion with a human QA", "Stage completion with the AI reviewer only" | The gates depend on whether a remark is open, closed or reopened, and on whether QA or the developer typed `Looks correct`. The specs never say where or how these states are recorded in `test-cases.md`, so "one open remark" and "QA confirmed" cannot be set up in a test or checked by a gate. With Q5 (B), the developer enters remarks and confirmation on QA's behalf, and the specs do not say whether this is allowed for closing and confirming. | review/spec.md:52, :78, :119-129; clarifications.md Q5, Q7, Q18, Q27 | Say what the stored record is (for example a status per remark: open / answered / closed, and a confirmation block in `test-cases.md` like the summary confirmation in `clarifications.md`). Add a scenario where the developer closes a remark and confirms on QA's behalf. Leave the exact syntax to the design. |
| S4 | major | test-cases/document › "Every scenario has a test case"; test-cases/review › "Late scenarios get test cases" | Coverage errors are reported "as an error", but the specs never say when the test-case check runs or what it blocks: writing `design.md`, archiving, or nothing. So a scenario added late without test cases (Q30) might not stop the archive at all. A test case with a missing label or no Then has the same problem. | document/spec.md:19, :42; review/spec.md:132-139; coverage/spec.md:36 | State which gates enforce the test-case check, for example "the design gate and the archive gate block while the test-case check reports an error". Add a scenario such as "Late scenario without test cases blocks the archive". |
| S5 | major | workflow/test-case-schemas | Q17 (A) and Q23 ask for switching between the two test-case schemas in the middle of a change, if that is easy. The confirmed assumption is: do it only if both schemas have the same steps, otherwise drop it and record it as out of scope. The specs make the two schemas identical in artifacts but neither specify switching nor record it as out of scope. Neither developers nor QA can tell whether to build it or test it. | test-case-schemas/spec.md:23-33; clarifications.md Q17, Q23, Main round assumptions | Either add a requirement with scenarios (switch AI-QA ↔ human-QA before the stage is complete; refused after it is complete, with the message shown), or add an explicit line that switching is out of scope for this change. |
| S6 | major | workflow/schema-starter › "The menu offers three choices" | The specs do not cover the developer dismissing the menu, picking a free-text "Other" answer, or answering something that maps to no schema. Claude Code menus always allow these. Nor do they say whether `lean` is offered: the confirmed assumption says it is not, but no scenario shows it. | schema-starter/spec.md:24-34; Main round assumption "Стартер предлагает выбор только между обычной схемой и двумя новыми" | Add scenarios: "Menu dismissed: no change is created and the agent waits for a choice", and "Free-text answer: the agent asks again with the three choices". Add a line that `lean` is not offered and is used only when it is named explicitly. |
| S7 | major | workflow/schema-starter › "Creating a change without a schema starts the menu" | The specs never say which command the hook watches ("the command that creates a change"). They also do not say which forms count as naming a schema (`--schema x`, `--schema=x`, a schema passed through the kit's openspec wrapper or `/opsx:new`). These cases cannot be written as hook tests without asking. | schema-starter/spec.md:10, :14, :20; clarifications.md Q22 ("детерминированность") | Name the watched command or commands and the accepted forms of naming a schema. Add a scenario for the `--schema=lean` form and one for the wrapper path. |
| S8 | major | test-cases/review › "What the AI QA reviewer checks", "The AI review loop runs at most three times" | The loop stops on READY, but the specs never say what makes the verdict READY. Only "Missing error case" says NOT-READY. "Missing boundary values" and "Vague outcome" give no verdict, and findings have no severity. The specs also do not say whether findings the developer has already accepted count against READY on the next run. | review/spec.md:19-49 | Define READY (for example "no finding of severity major or higher, ignoring findings accepted by the developer"). Add the verdict to the two scenarios that lack it. |
| S9 | minor | test-cases/review › "What the AI QA reviewer checks" | The checklist ends with "and the like", which is open-ended and cannot be tested. "Missing permission" is not in any answer. Add a scenario such as "Repeated submission not covered is a finding". |
| S10 | minor | test-cases/coverage › "References to archived test cases are not reported" | Q34 silences only references to archived cases.
